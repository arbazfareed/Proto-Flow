# Performance benchmarks

PF-T705 uses deterministic, in-memory project fixtures and Chromium so performance checks run without cloud services or app credentials. The canvas workload uses the same Konva renderer and viewport culling helpers as the editor. Feature timings call the production panel, repeater virtualization, expression, flow-layout, and Zustand store implementations.

## Run locally

```powershell
npm ci
npx playwright install chromium
npm run benchmark:performance
```

`benchmark:performance` type-checks and builds with source maps, generates a source-map explorer report, runs Vitest microbenchmarks, then executes the browser workload. The browser benchmark defaults to ten seconds per interaction mode and a five-minute heap soak. To smoke-test the wiring without waiting for the full run:

```powershell
$env:PF_BENCHMARK_MODE_MS = "200"
$env:PF_BENCHMARK_SOAK_MS = "1000"
npm run benchmark:axure-parity
```

Delete those environment variables after the smoke run to restore the full acceptance duration.

## Workloads and hard limits

| Workload | Deterministic fixture | Required result |
|---|---|---:|
| Canvas FPS | 20-widget medium; 500-widget large | >= 55 FPS |
| Canvas FPS | 1,000-widget stress | >= 45 FPS |
| Feature FPS | Panels, repeaters, expressions, nested panels, full mix, and flow diagram | >= 50 FPS |
| Pan / zoom | Per-operation P95 including viewport culling and draw | < 16 ms |
| Dynamic panels | 20 panels, 5 states, 10 widgets/state | < 50 ms per switch |
| Repeaters | 500 rows × 5 template widgets; virtualized viewport render | < 200 ms |
| Expressions | 200 expression widgets; per-expression evaluation average | < 1 ms |
| Flow diagram | 100 screens / 300 transitions | < 500 ms layout |
| Store | Add 100 widgets; undo/redo 50 snapshots; select 500 IDs | < 1,000 / 500 / 16 ms |
| Bundle | Production output excluding source maps | < 15 MiB total; < 2 MiB JavaScript gzip |
| Startup | Cold React mount / warm median of 3 reloads | < 3 s / < 1 s |
| Memory | Five-minute full-mix heap soak | < 20 MiB growth |

Scene FPS is additionally compared with the 60 FPS reference: a drop greater than 10% fails. Bundle growth above 5% warns and above 10% fails; the absolute byte budgets remain hard limits. Panel, repeater, expression, flow-layout, and startup timings fail when more than 20% slower than their recorded references, subject to the absolute limits above. Heap growth more than 50% above the 10 MiB reference fails, as does exceeding the 20 MiB hard limit.

## Baselines, reports, and CI

- [`baseline.json`](./baseline.json) is the versioned threshold/reference source. Change it in the same PR only when the performance budget is intentionally revised.
- [`trends.json`](./trends.json) stores the latest 100 CI/local run summaries. CI uploads the updated history with the run artifacts.
- `reports/PERF-AXURE-PARITY.md` and `reports/axure-parity-latest.json` contain detailed per-run measurements.
- `reports/bundle-map.html` is generated by source-map-explorer.
- The `Performance benchmarks` workflow runs on every PR targeting `main`; failures block the check. It uploads reports and posts/updates a PR summary comment.

Measurements are hardware- and browser-dependent. The job pins Chromium through Playwright and applies absolute limits as well as regression thresholds; compare reports from the same runner image when investigating a change. The in-memory `.pflow`-shaped fixtures are generated in `scripts/axure-parity-benchmark.js` to keep large datasets compact and deterministic rather than checking in multi-megabyte data files.
